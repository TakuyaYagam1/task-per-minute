# Аккаунты и почта

Новый аккаунт становится доступен после подтверждения email. Пользователь
регистрирует уникальный логин, почту и пароль, открывает ссылку из письма,
подтверждает адрес и входит. Логин отображается в рейтинге. Пароль содержит
10-128 символов, включая хотя бы одну строчную и одну прописную букву,
десятичную цифру и знак пунктуации или символ. Пробел не считается таким
знаком.

Email должен быть адресом одного ящика без отображаемого имени. Часть до `@`
должна быть ASCII dot-atom длиной 1-64 символа. Домен должен состоять из ASCII
DNS-меток, разделенных точками, и содержать минимум две метки. Последняя метка
должна состоять только из ASCII-букв и содержать не менее двух символов либо
иметь вид `xn--...`. `localhost` и домены-литералы не допускаются.

Для аккаунта без подтвержденного email подсказка об активации появляется только
после проверки верного пароля. Неверный пароль получает общее сообщение об
ошибке входа. Сессия создается только после подтверждения email. Ссылка
одноразовая и действует 24 часа; повторная отправка доступна раз в минуту и
заменяет предыдущую ссылку.

На странице из письма подтвердите адрес кнопкой. После успеха можно нажать
кнопку входа или дождаться автоматического перехода через 5 секунд.

После регистрации кнопка "Не пришло письмо?" повторно отправляет письмо
прямо на этой странице. Между отправками действует пауза 60 секунд с таймером.
Адрес сохраняется только в памяти страницы; пароль после регистрации очищается.

После правильного пароля форма входа показывает кнопку для повторной отправки
письма на адрес, сохраненный в аккаунте. Кнопка доступна раз в минуту. Запрос с
неверным паролем не отправляет письмо и получает общее сообщение об ошибке.

Тексты писем находятся в `backend/internal/adapter/outbound/mail/templates/`.
У каждого письма есть HTML- и текстовая версия. Шаблоны включены в бинарный
файл через `go:embed`; после изменения требуется пересборка backend.
HTML-подстановки экранируются стандартным `html/template`.

## Resend

```env
EMAIL_PROVIDER=resend
EMAIL_FROM=noreply@example.org
APP_PUBLIC_URL=https://example.org
EMAIL_TIMEOUT=10s
RESEND_API_KEY=<secret>
```

Домен отправителя должен быть [подтвержден в Resend](https://resend.com/docs/dashboard/domains/introduction).
На подтвержденном домене можно выбрать адрес отправителя, например `noreply`.
Отключите click tracking для писем подтверждения, чтобы перенаправление не
изменяло ссылку. Токен передается во фрагменте URL и удаляется страницей
подтверждения из адресной строки.

`APP_PUBLIC_URL` - публичный HTTPS origin фронтенда без пути, query и fragment.
HTTP разрешен только для localhost и loopback IP при локальной разработке.
Если `EMAIL_PROVIDER` пуст, `RESEND_ENABLED=true` выбирает Resend. Явное значение
`EMAIL_PROVIDER` имеет приоритет. Без провайдера доставка отключена.

## SMTP

```env
EMAIL_PROVIDER=smtp
EMAIL_FROM=noreply@example.org
APP_PUBLIC_URL=https://example.org
EMAIL_TIMEOUT=10s
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_USERNAME=<smtp-user>
SMTP_PASSWORD=<secret>
SMTP_TLS_MODE=starttls
```

Режим `starttls` требует STARTTLS; `tls` включает TLS сразу при соединении.
Сертификат и имя сервера проверяются в обоих режимах. Для relay без авторизации
оставьте имя пользователя и пароль пустыми. Пароль передается без обрезки пробелов.

`EMAIL_PROVIDER=disabled` отключает отправку. Регистрация и повторная отправка
возвращают 503. При ошибке доставки уже созданного аккаунта запросите новое
письмо кнопкой "Не пришло письмо?" на странице регистрации. Повторная отправка
также доступна на странице входа после проверки правильных данных аккаунта.

## Настройки аккаунта

Настройки доступны только владельцу действующей сессии. Смена логина, пароля
и начало смены почты требуют текущий пароль. Ошибка этого пароля не завершает
сессию. Логин меняется вместе с резервом имени, без изменения ID игрока и его
результатов. После смены пароля текущая сессия и CSRF-токен заменяются; прежняя
сессия перестает действовать.

Для смены почты тот же адаптер Resend или SMTP отправляет шестизначный код на
новый адрес. Код действует 10 минут, повторное письмо доступно через 60 секунд.
Разрешены пять отправок и пять неудачных попыток подтверждения за час.
Отмена, повторная отправка и перезагрузка страницы не сбрасывают эти лимиты.
В базе сохраняется только хеш кода. До подтверждения действует прежняя почта;
новый адрес проверяется на занятость повторно при подтверждении.

После подтверждения почты сессия обновляется, а на прежний адрес отправляется
уведомление. Если уведомление не доставлено, API сообщает об этом отдельно:
уже сохраненная новая почта при этом остается действующей. Ошибка отправки
самого кода возвращает 503 и не выдается за успешную доставку.

Аватары используют префикс `avatars/` в существующем закрытом S3-бакете.
Дополнительный бакет и новые учетные данные не нужны. Сервер принимает JPG,
PNG, GIF и MP4 до 5 MiB, проверяет размеры и содержимое, удаляет метаданные и
сохраняет анимацию GIF. Изображения ограничены 4096 пикселями по каждой стороне;
для GIF также ограничены число кадров и суммарное число пикселей.
Аватар выдается владельцу через API с `Cache-Control: private, no-store`.

В MP4 поддерживаются кодеки H.264, HEVC и MPEG-4. Действуют ограничения:
10 секунд, 60 кадров в секунду, 1920 пикселей по каждой стороне и 2 073 600
пикселей на кадр. FFmpeg проверяет и преобразует ролик
в H.264 без звука и исходных метаданных, до 512 x 512 пикселей и 30 кадров в
секунду. Обработка ограничена по времени; один экземпляр backend обрабатывает
одно видео одновременно. В браузере ролик повторяется без звука.
При включенном уменьшении движения ролик изначально приостановлен.
Backend требует `ffmpeg` и `ffprobe` в PATH. Docker-образ собирает закрепленную
версию FFmpeg из исходника после проверки контрольной суммы и подписи выпуска.
Отдельная проверка CI запускает тесты кодеков с этими же бинарными файлами
в контейнере без доступа к сети.

Выбор аватара сразу запускает сохранение. Ошибка замены сохраняет прежний
аватар. Удаление убирает его из профиля сразу, а файл удаляется фоновой очередью
с повторными попытками при сбое S3. Эта очередь также обрабатывает старые
файлы после замены, незавершенные загрузки и аватары удаленных аккаунтов.

Перед запуском новой версии примените миграции `000037_player_account_settings.sql`,
`000038_player_avatars.sql` и `000039_player_avatar_video.sql`.
Откат ограничен, чтобы не потерять начатые
подтверждения почты или задания очистки S3. При наличии таких данных используйте
исправление вперед. Миграция 39 не откатывается, пока остаются объекты MP4,
включая ожидающие фоновой очистки. Настройка 2FA и восстановление забытого
пароля в этот этап не входят.

## Переход и проверка

Остановите старые экземпляры backend, примените миграцию
`000035_player_accounts.sql`, затем запустите новое приложение. Это исключает
создание игроков старым кодом во время заполнения реестра имен.
Старые игроки и результаты сохраняются, их имена резервируются без учета
регистра. Регистрация не присваивает существующую запись игрока. Старые сессии
без подтвержденного аккаунта отклоняются, вход только по нику возвращает 410.

Откат миграции запрещен при наличии аккаунтов. Старый образ приложения снова
открывает вход по нику, поэтому такой откат небезопасен для публичного сервиса.
Предпочтительнее исправление с обновлением вперед или режим обслуживания.

Локальные тесты используют синтетические адреса, перехват писем и SMTP с TLS
на loopback. Они не доказывают доставку в реальный почтовый ящик. Перед запуском
проверьте регистрацию на целевом домене и получение письма владельцем тестового
адреса. OAuth, MFA и восстановление пароля в этот этап не входят.

## Удаление аккаунта

Удаление игрока администратором очищает связанный аккаунт: email, хеш пароля,
данные подтверждения и резерв исходного логина. Почту и логин можно использовать
для новой регистрации с новым подтверждением. Новая регистрация не наследует
идентификатор игрока или его результаты. Историческая запись игрока с отметкой
удаления, результаты соревнований и журнал действий сохраняются.

Активная сессия отзывается в той же транзакции. Для уведомления браузера сервер
временно хранит только хеш отозванного токена и срок его действия, без email,
пароля или связи с аккаунтом. Ответ `401` с кодом `player.account_deleted`
отличается от обычного истечения сессии. Активная вкладка проверяет сессию каждые
10 секунд и при возвращении фокуса, затем показывает сообщение об удалении
аккаунта администратором. Кнопка "Понятно" переводит на страницу входа.
Истекшие хеши больше не влияют на авторизацию и удаляются пакетами при
последующих удалениях игроков; без новых удалений они могут оставаться в таблице.

Миграция `000036_player_account_deletion.sql` очищает учетные данные и резервы
ников у уже удаленных игроков. Перед обновлением остановите старые экземпляры
backend; затем примените миграцию и запустите новую версию. Очистка необратима,
поэтому миграция запрещает откат. При необходимости используйте исправление
вперед. Проверьте отсутствие аккаунтов, связанных с удаленными игроками,
и новую регистрацию с освобожденными данными на тестовом стенде.

## Локальные проверки

Из `backend` запустите проверки аккаунтов и миграции с отдельным PostgreSQL:

```sh
go test -race -tags=integration -count=1 ./integration_test/player
go test -race -tags=integration,account_e2e -count=1 ./integration_test/accountflow
```

Для браузерного сценария из `frontend`:

```sh
E2E_ACCOUNT_FULL_STACK=1 npm run test:e2e -- e2e/account-full-stack.spec.ts --workers=1
```

Нужны локальный Docker-совместимый runtime, зависимости проекта, закрепленные
Go и Chromium. Запускайте проверки с окружением без рабочих секретов. Браузерный
режим сам поднимает отдельные API, frontend и PostgreSQL, перехватывает письмо
в памяти и закрывает их после теста. Реальный почтовый провайдер не вызывается.
